# ADR-001: Enforce Project Role Checks in a Shared Guard, Not in Every Service

## Why this is a real decision

Both options are defensible. Checking the caller's role inside a `RolesGuard` before
the controller runs is the conventional NestJS pattern, but a competent engineer could
just as reasonably check `req.user`'s role inside each service method instead, since
the service already loads the entities needed to make finer-grained decisions (e.g.
"is this user the author of _this specific_ comment"). Neither option is obviously
wrong — the guard buys consistency and the per-service check buys flexibility close to
the data, which is why this is worth recording rather than assuming.

## Context

- The domain has five role-checked resources (projects, project members, tasks, tags,
  comments) across more than 20 routes, and every one of them uses the same four-value
  role enum (`owner` / `admin` / `member` / `viewer`) defined on `project_members`.
- Phase 4 will be built by more than one developer over multiple weeks; new endpoints
  will be added after this decision is made, not just before it.
- A role check requires a database read (`SELECT role FROM project_members WHERE
user_id = ? AND project_id = ?`) before most other logic can run — it's a security
  check, not a business rule, and it is the same query shape everywhere.
- A handful of checks are _not_ project-role checks at all — e.g. "only the comment's
  author may edit it" depends on a column on the loaded `comments` row, not on
  `project_members`.
