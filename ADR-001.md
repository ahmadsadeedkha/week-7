# ADR-001: Enforce Project Role Checks in a Shared Guard, Not in Every Service

## Why this is a real decision

Both options are defensible. Checking the caller's role inside a `RolesGuard` before
the controller runs is the conventional NestJS pattern, but a competent engineer could
just as reasonably check `req.user`'s role inside each service method instead, since
the service already loads the entities needed to make finer-grained decisions (e.g.
"is this user the author of _this specific_ comment"). Neither option is obviously
wrong — the guard buys consistency and the per-service check buys flexibility close to
the data, which is why this is worth recording rather than assuming.

## Context

- The domain has five role-checked resources (projects, project members, tasks, tags,
  comments) across more than 20 routes, and every one of them uses the same four-value
  role enum (`owner` / `admin` / `member` / `viewer`) defined on `project_members`.
- Phase 4 will be built by more than one developer over multiple weeks; new endpoints
  will be added after this decision is made, not just before it.
- A role check requires a database read (`SELECT role FROM project_members WHERE
user_id = ? AND project_id = ?`) before most other logic can run — it's a security
  check, not a business rule, and it is the same query shape everywhere.
- A handful of checks are _not_ project-role checks at all — e.g. "only the comment's
  author may edit it" depends on a column on the loaded `comments` row, not on
  `project_members`.

## Options Considered

**Option A — Guard-based RBAC.** A `RolesGuard` reads `@Roles('owner','admin')`
metadata off the route handler, resolves the project ID from the route params, looks up
`project_members`, and rejects with `403`/`404` before the controller body runs.

- Advantage: protection is declarative and visible in a code review — a route with no
  `@Roles()` decorator (or an explicit `@Public()`) stands out, so a missing check is a
  diff, not a silent gap.
- Disadvantage: the guard only has route params to work with, so it cannot answer
  entity-specific questions like "is this user the comment's author" without an extra
  query of its own — those checks still need to happen somewhere else.

**Option B — Per-service checks.** Each service method receives the caller's ID and
role and checks them manually, e.g. `if (role === 'viewer') throw new
ForbiddenException()`, right next to the business logic that uses the loaded entity.

- Advantage: full access to the already-loaded entity, so ownership checks (comment
  author, task assignee) are a single `if` with no extra query.
- Disadvantage: the same four-role check is copy-pasted into >20 methods across five
  services; a new endpoint that forgets the check compiles, runs, and returns data —
  the gap is invisible until someone notices unauthorized access in practice.

**Option C — No centralized layer ("change nothing"), ad hoc per controller.** Viable
only while the API is very small (roughly under five routes, before the shared-role
pattern repeats enough to be worth extracting) — already not viable here, since this
domain starts at 20+ routes on day one of Phase 4.
